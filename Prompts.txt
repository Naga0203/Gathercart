# PHASE 0: Project Discovery, UI Analysis and Development Planning

Act as a Senior Software Architect and Full-Stack Technical Lead.

Your task is to thoroughly inspect the existing project before making any modifications.

## Project Context

We are building a grocery group-buying platform.

Technology stack:
- Frontend: React + TypeScript + Vite.
- Backend: Java + Spring Boot.
- Database: MySQL running locally.
- ORM: Spring Data JPA / Hibernate.
- API: REST APIs.

The UI reference screenshots are located in the `screens/` folder.

## Step 1: Inspect the repository

Inspect:
- Existing frontend structure.
- Existing backend structure.
- Dependencies and configurations.
- Build tools.
- Existing routes and components.
- Database configurations.
- Existing APIs and business logic.
- Environment variables and configuration files.

Do not modify or delete anything.

## Step 2: Analyze UI screens

Inspect every screenshot inside `screens/`.

For each screen, identify:
- Screen name and purpose.
- UI components.
- Navigation relationships.
- User interactions.
- Forms and validation requirements.
- Data displayed.
- Backend functionality required.
- Possible database entities.

Identify reusable components and common layouts.

Treat the screenshots as the primary design reference.

## Step 3: Identify business features

Categorize the application into:
- Core MVP features.
- Supporting features.
- Authentication and authorization.
- Administrative features, if present in the references.
- Future enhancements.

Identify dependencies between features.

## Step 4: Database planning

Propose the initial database entities and relationships.

Identify:
- Entity attributes.
- Primary and foreign keys.
- One-to-one, one-to-many and many-to-many relationships.
- Constraints.
- Indexes.
- Ownership relationships.
- Data integrity requirements.

Do not create the schema yet.

## Step 5: API planning

Identify the API endpoints required for the MVP.

For each endpoint, provide:
- HTTP method.
- Endpoint.
- Purpose.
- Request structure.
- Response structure.
- Validation rules.
- Expected error responses.

## Step 6: Development roadmap

Create:
- DEVELOPMENT_PLAN.md
- DATABASE_DESIGN.md
- API_CONTRACT.md
- PROJECT_STRUCTURE.md

These documents should describe the proposed implementation.

## Rules

1. Do not generate the entire application.
2. Do not modify existing source files.
3. Do not install dependencies.
4. Do not assume features that are not supported by the screenshots or requirements.
5. Clearly identify missing information.
6. Preserve existing architecture wherever reasonable.

## Expected Output

Provide:
1. Repository analysis.
2. Screen inventory.
3. Feature inventory.
4. Proposed architecture.
5. Database design.
6. API plan.
7. Feature dependency order.
8. Identified risks and assumptions.

Stop after completing the analysis and wait for approval before proceeding.

# PHASE 7: Authentication, Authorization and Application Security

Act as a Senior Java Spring Boot Security Engineer and React Security Engineer.

Implement production-conscious authentication and authorization for the existing application.

Do not rewrite completed business features unnecessarily.

## 1. Authentication architecture

Use:
- Spring Security.
- JWT authentication.
- Secure password hashing using BCrypt or an appropriate password encoder.
- MySQL user persistence.

Implement:
- Registration.
- Login.
- Logout.
- Current user information.
- Token validation.
- Appropriate token expiration and renewal strategy.

Choose a secure token storage approach. Prefer HttpOnly, Secure cookies where the deployment architecture supports them, and protect cookie-based authentication against CSRF.

Do not store sensitive credentials in localStorage.

## 2. User management

Implement the required user entity and relationships.

Potential attributes:
- User ID.
- Name.
- Email.
- Password hash.
- Role.
- Account status.
- Created date.
- Updated date.

Enforce unique email addresses.

Never return password hashes in API responses.

## 3. Authorization

Implement role-based authorization based on the actual requirements.

Potential roles:
- CUSTOMER.
- ADMIN.

Enforce permissions in Spring Security and service-level ownership checks.

Users must not be able to:
- Access another user's protected information.
- Modify another user's cart or orders.
- Join groups on behalf of unauthorized users.
- Perform administrative operations without permission.

Do not rely on frontend route protection alone.

## 4. Frontend integration

Implement:
- Registration page.
- Login page.
- Logout.
- Authentication state.
- Current user context.
- Protected routes.
- Unauthorized access handling.
- Session expiration handling.

Preserve existing UI design.

## 5. Integrate authentication into existing features

Update:
- Cart ownership.
- Group ownership.
- Group participation.
- Order ownership.
- Profile data.

Remove temporary hardcoded user identities and test-only ownership logic.

Do not break previously completed functionality.

## 6. Security testing

Test:
- Invalid credentials.
- Duplicate registration.
- Expired tokens.
- Unauthorized access.
- Role restrictions.
- Cross-user data access.
- Password handling.
- Session expiration.
- CSRF protection where applicable.
- CORS configuration.

## Completion Criteria

Authentication and authorization must be enforced by the backend.

All existing business workflows must continue working with authenticated users.

Document the security architecture and configuration.

# FEATURE EXECUTION PROTOCOL

We are following an incremental full-stack development approach.

Before starting the next feature, inspect DEVELOPMENT_PLAN.md and the existing codebase.

For the selected feature:

1. Identify the exact UI screens involved.
2. Identify frontend components and routes.
3. Identify backend controllers, services and repositories.
4. Identify database entities and relationships.
5. Define the API contract.
6. Identify dependencies on completed features.
7. Implement frontend and backend in parallel.
8. Integrate them using actual REST APIs.
9. Run frontend and backend tests.
10. Verify database operations.
11. Fix all critical issues.
12. Update project documentation and DEVELOPMENT_PLAN.md.

IMPORTANT RULES:

- Do not rebuild completed functionality.
- Do not modify unrelated modules.
- Do not introduce mock data when actual APIs are available.
- Do not create placeholder functionality.
- Do not hardcode business data.
- Do not bypass backend validation.
- Do not claim functionality is complete without testing.
- Preserve existing design and architecture.
- Ask before making major database or architectural changes.

Work only on the selected feature.

At the end, provide a concise implementation report and wait for approval before beginning the next feature.
